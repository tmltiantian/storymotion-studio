# 统一视频生产流水线设计

## 目标

把当前小说漫剧、原创宠物短剧和参考视频复刻三条纵向实现，收敛为一个稳定的生产模型：

`输入 -> 脚本 -> 分镜 -> 素材 -> 音频 -> 视频 -> 剪辑 -> EVAL -> 返修/交付`

三种项目只在输入理解和素材约束上不同，后续阶段使用相同协议、状态、缓存和返修语义。

## 设计原则

- 统一生产协议和调度，不强行统一三种模式的提示词。
- 音频优先：对白先生成真实时长，再绑定说话动作、口型和镜头窗口。
- 每个阶段写入结构化状态，支持停止、续跑和局部返修。
- 供应商只作为适配器：文本、Seedream、Seedance、Seed-TTS、FFmpeg/OpenMontage 可替换。
- 第一阶段复用已经验证的旧执行器；迁移测试通过前不删除成熟能力。
- 只有直接依赖、CLI 引用和测试覆盖均证明已被替代的包装层才能删除。

## 统一项目规范

`ProjectSpec` 是所有模式的唯一用户输入协议：

- `project_id`、`title`、`mode`
- `input`：创意文本、小说文件或参考视频配置
- `output_dir`
- `target`：时长、画幅、分辨率、帧率、镜头数量
- `characters`：角色标识、参考图、音色和性格约束
- `providers`：文字、图片、视频、语音和剪辑选择
- `policies`：是否联网、音频优先、EVAL 门禁和最大返修次数
- `mode_options`：只属于当前模式的参数

规范保存为 `project.json`。敏感凭据永远不进入规范或报告。

## 统一制作包

每个项目输出 `production_package.json`，包含：

- 项目规范哈希与版本
- 标准九阶段状态
- 由模式适配器生成的脚本、分镜、角色、场景、道具和时间轴路径
- 每个阶段的输入签名、产物、复用状态、阻塞原因和执行器
- 当前 `next_stage`
- 最终成片和 EVAL 报告

阶段状态仅允许：`pending`、`ready`、`running`、`passed`、`failed`、`blocked`、`stale`。

## 三种模式

### Original

把创意扩写成剧本和分镜。第一版复用 `pet_sitcom` 的成熟音频优先、角色一致性、逐镜生成、审核和合成能力。

### Novel

读取小说，提炼人物、场景和事件并改编成剧本。第一版复用 `project_runner` 的小说规划、角色资产、网关视频、配音和 OpenMontage 合成。

### Replica

读取参考视频或参考项目配置，提取镜头边界、构图、动作、道具接触和音频政策，只替换被指定的角色与素材。第一版复用 `source_locked_cat_replica`；旧 `pet_replica_cli` 保留为兼容适配器，待项目迁移后删除。

## 标准阶段

1. `concept`：确认创意、小说或参考源。
2. `script`：形成可执行剧本与角色关系。
3. `storyboard`：形成逐镜时间线和动作约束。
4. `assets`：生成或绑定角色、场景、道具锚点。
5. `audio`：生成固定音色、真实时长、字幕和口型窗口。
6. `video`：逐镜生成并记录候选、模型和输入签名。
7. `edit`：剪辑、转场、字幕、音效、配乐和混音。
8. `eval`：检查身份、场景、解剖、物理、动作、口型、声音和转场。
9. `deliver`：局部返修全部通过后封存成片和报告。

模式适配器可以把一个标准阶段映射为多个旧步骤，也可以把不适用的阶段作为已满足的结构化结果，但不能伪造产物。

## 统一入口

正式入口为：

```text
factory create --mode original|novel|replica ...
factory run PROJECT [--through STAGE] [--enable-live]
factory resume PROJECT [--enable-live]
factory status PROJECT
factory review PROJECT
factory publish PROJECT
```

`create` 只写规范，不调用收费模型；`run` 默认干跑，只有显式 `--enable-live` 才允许云端生成。

## 续跑与返修

- 阶段输入签名由规范、上游产物哈希和执行器版本组成。
- 签名和产物均有效时复用阶段；输入变化时标记当前及下游为 `stale`。
- EVAL 输出按镜头和问题类型组织的 repair tickets。
- 返修只使受影响镜头、对应合成和最终验收失效，不重跑无关素材。

## 清理策略

第一轮清理只删除缓存、无引用包装和重复入口，不删除历史产物与迭代文档。代码迁移顺序：

1. 新建统一协议、状态存储、模式注册表和统一 CLI。
2. 通过适配器接入三种现有流程，并写契约测试。
3. README 改为统一入口，旧命令移动到兼容章节。
4. 使用真实旧项目执行无网络状态迁移，确认成片和断点状态可识别。
5. 删除已被统一入口完全覆盖、且不再被导入的 CLI 包装层。

成熟的网关、TTS、媒体检查、生成、合成和 EVAL 实现继续保留在原模块，后续再按共享阶段逐步内聚。

## 验收标准

- 三种模式均能创建同格式 `project.json` 和 `production_package.json`。
- 一个 CLI 能创建、运行、续跑和查看三种项目。
- 默认操作不产生云端费用。
- 现有宠物音色、Seedance、合成和 EVAL 测试继续通过。
- README 首页只讲统一流程，旧命令不再作为首选入口。
- 清理报告列出保留、兼容、删除三类模块及证据。
